# Team and agent workflow

Status: draft (adopt after the ADR lock on 3 Nov 2026)
Last reviewed: 2026-11-02
Owner: both developers (BE and FE)

This is how the two of us work in this repo, with and without AI coding agents. It is written to be followed by people and read by agents. Setup of everything described here is done by `docs/workflow/SETUP-AGENT-WORKFLOW.md`.

## 1. Principles

1. **Review attention is the bottleneck, not code generation.** We run at most two agent sessions each. More sessions only produce more unreviewed code.
2. **Contract first.** `openapi.yaml` and the migrations are the fence. Agents implement against them. CI proves nothing drifted.
3. **`make verify-full` is the definition of done.** It runs in CI on a protected `main`. Prompts, rules files and hooks are reminders; CI is the gate.
4. **Security lane is never delegated.** Auth, sessions, KTP encryption and key handling are read line by line by the person who did not write them.
5. **One source of truth per fact.** System facts live in `docs/`. Everything else links to them.
6. **Built for handover.** Diskominfo staff who did not write the code must be able to run, patch and restore it.

## 3. Roles and ownership

| Area | Writes | Reviews before merge |
|---|---|---|
| `api/` (handlers, queries, migrations) | BE | FE |
| `web/` | FE | BE |
| `openapi.yaml` | whoever has the open contract task, one at a time | the other, same day |
| Auth, sessions, RBAC, TOTP, KTP encryption, keys | BE drafts | **both read every line** |
| Makefile, CI, `AGENTS.md`, `.claude/`, handover docs | shared, by PR | the other |

`CODEOWNERS` lists **both** developers on every path (`* @BE @FE`). A PR author cannot approve their own PR, so this makes the other person the required reviewer for everything and avoids a deadlock that per-folder owners would cause.

## 4. Environments and data rules

- Agents work against a **local dev database with synthetic data**. No production credentials, no real KTP numbers, no real `.env`, no access to the VPS.
- Production secrets (KEK, VPS accounts, SMTP if any) are held by the people who own them (named in `docs/handover/OWNERS.md`), never in the repo or in an agent session.
- `.env` is git-ignored; `.env.example` is committed with fake values.
- Run agents in a dev container or with the sandbox on when possible. Deny rules reduce accidents but are not a security boundary for shell commands.
- Open question, answer in writing from Diskominfo: is sending source code to an external AI service allowed? Until answered, code stays private and no real data reaches an agent.

## 5. The Makefile is the interface

| Target | What it does | Needs DB superuser? |
|---|---|---|
| `make gen` | regenerate everything: sqlc, oapi-codegen (Go), openapi-typescript (web) | no |
| `make gen-check` | run `gen`, fail if generated files differ from what is committed | no |
| `make lint` | gofmt check, `go vet`, golangci-lint, web lint and `svelte-check` | no |
| `make test` | fast tests: `go test -race -short`, web unit tests | no |
| `make test-full` | all Go tests, including those that need Postgres | yes (throwaway DB) |
| `make vuln` | `govulncheck`, `npm audit` (prod, high) | no |
| `make build` | compile the Go binary and build the web app (adapter-node) to prove the production build works; logs the build time | no |
| `make release VERSION=vX.Y.Z` | build images, SBOMs, checksums and the deploy bundle (used by `release.yml`; can be run locally) | no |
| `make smoke URL=...` | post-deploy checks against a running stack (health, key pages, one authenticated call on staging) | no |
| `make verify` | `gen-check` + `lint` + `test` + `vuln` (fast, run constantly) | no |
| `make verify-full` | `verify` parts + `test-full` + `db-test` + `db-docs-check` + `docs-check` (what CI runs) | yes |
| `make db-*` | existing: `db-up`, `db-init`, `db-migrate`, `db-new`, `db-generate`, `db-test`, `db-docs`, `db-erd`, `db-docs-check` | see schema doc |

Convention: a Go test that needs Postgres calls `testing.Short()` and skips, so `make verify` stays fast and `make test-full` runs everything.

An agent may say "done" only after pasting the tail of a passing `make verify` (and `make verify-full` if it touched SQL or migrations).

## 6. Task lifecycle (every task)

1. **Issue.** Use the task template: goal, FR/NFR ids, files expected to change, acceptance checks. Five lines is enough. For anything touching schema or auth, the human writes a short `SPEC` in the issue.
2. **Contract PR first, if the API changes.** Edit `openapi.yaml` only, run `make gen`, commit regenerated files, open a small PR. The other person reviews it the same day. After it merges, both sides implement in parallel: BE implements strict-server handlers and queries; FE builds against a Prism mock, then Prism proxy, then the real server.
3. **Worktree per task.** `claude -w <issue-id>` (or `git worktree add`). Worktrees isolate files, not ports or databases, so give each its own ports and database name (see section 7).
4. **Plan, then implement.** Ask the agent for a plan and read it before it writes code. Implement in a fresh session.
5. **Verify.** Run `make verify` until it exits 0. Read edited tests for weakened assertions.
6. **PR.** One task per PR, small, from the template. The author explains the diff in the PR text, including "what I do not yet understand about this diff".
7. **Review.** The other person reviews. Optional extra pass first: a second fresh session using a read-only reviewer subagent. Its usefulness is unproven, so it never replaces the human.
8. **Merge.** Squash-merge, one branch at a time. CI reruns on `main`. Delete the branch and the worktree.

## 7. Branches, commits, PRs, worktrees

- Branch names: `feat/<issue-id>-short-title`, `fix/...`, `chore/...`, `docs/...`.
- Commit messages: short imperative subject; body explains why when not obvious.
- PR size: if a reviewer cannot hold it in their head in one sitting, split it. Contract changes, migrations and generated-code updates are separate PRs from feature code where possible.
- `main` is protected (section 12). No direct pushes, no force-push.
- Ports and databases per worktree: BE `8080+n`, web `5173+n`, database `bappelitbangda_dev_<issue-id>`, where `n` is the worktree number. Set them in that worktree's `.env`. `.worktreeinclude` copies the local `.env` into new worktrees.
- At most two agent sessions each at a time. Each session loads its own configuration, so parallel sessions also multiply cost.

## 8. Contract-first rules

- `openapi.yaml` is the single source of truth. Never hand-edit generated Go or TypeScript.
- Only one open contract PR at a time.
- Generated output is committed. `make gen-check` fails CI if it is stale or hand-edited.
- Breaking changes (renamed field, changed status code) need an explicit note in the PR and the FE reviewer's approval.
- FE develops against Prism (`prism mock`, then `prism proxy`) so work does not wait for BE.

## 9. Database rules

- Never edit, delete or rename a migration that exists on `main`. Fix forward with a new migration. `scripts/check-migrations-immutable.sh` enforces this in CI.
- Every migration has a working `Down`.
- Risky changes use expand and contract across two releases.
- New table: `COMMENT ON TABLE`, an index on each foreign key, a line in migration `00009` and a test in `tests/privileges.sql` if the app must not edit or delete from it.
- New query: add it to `api/db/queries/`, run `make db-generate`, add a case to `tests/queries.sql`.
- New database rule: add a test in `tests/constraints.sql` that proves it fails when broken.
- Schema docs in `docs/schema/` are generated; `make db-docs-check` fails if they drift.

## 10. Working with agents

**Agents may:** write scaffolding, handlers, queries, tests, frontend components, docs drafts; run `make` targets; open branches.

**Agents may not, without a human decision:** add a dependency, add a table or column, change the contract beyond the task, touch auth, sessions, KTP encryption or keys beyond a draft, run destructive commands, or weaken or delete a test to make it pass.

**Agents never:** merge a PR, create or move a tag, publish a release, change repository, organization or branch-protection settings, edit workflow permissions, add secrets, or deploy. They may create branches, commit, push feature branches and open PRs (if a human has given them access to do so). Merging, tagging, releasing and deploying are human actions.

**Habits that matter:**
- The agent proves "done" with command output, not with a statement.
- The author reads the whole diff before asking for review.
- Friday "explain it back": each of us walks the other through a module they did not write. This is how we avoid code nobody understands at handover.
- Once a week, write one small core piece by hand.
- Keep `AGENTS.md` short. If a rule must never be broken, it belongs in CI or a deny rule, not only in prose.

## 12. Branch and tag protection (the restrictions)

Applied with a ruleset (or classic branch protection) on `main`. The rule applies to everyone, including administrators and owners. The rulesets are kept as code in `.github/rulesets/` and applied by a human with `scripts/github-apply-settings.sh` (dry-run first); agents never change repository settings.

| Rule on `main` | Setting | Reason |
|---|---|---|
| Changes only through a pull request | on, no direct pushes | every change is seen by a second person |
| Required approvals | 1, from a code owner (the other developer) | two-person review |
| Dismiss stale approvals when new commits are pushed | on | approval applies to what was reviewed |
| Require approval of the most recent push | on | the author cannot push after approval and merge |
| Required status checks | `verify-full (16)`, `verify-full (18)`, `build` | the gate (names appear after the first CI run, then add them) |
| Require branch to be up to date before merging | on | the checks ran on what will actually be merged |
| Require conversation resolution | on | review comments are not skipped |
| Require linear history | on | matches squash-only merging |
| Block force pushes | on | history is trustworthy |
| Block deletion of `main` | on | |
| Bypass list | empty | a rule that admins or tokens can bypass will not stop a bad push |
| Require signed commits | off for now | friction for a time-boxed team; revisit if Diskominfo requires it |
| Merge queue | not used | two developers do not need it |

| Rule on tags `v*` | Setting |
|---|---|
| Who may create | maintainers only, by agreement (agents never). The ruleset blocks updating and deleting tags; it does not technically restrict creation, which is limited only to people with write access |
| Update or delete an existing release tag | blocked |
| Tag must point to a commit on `main` | `release.yml` checks this and fails otherwise |

Honest limits: with two organization owners, an owner can still edit these rules. The ruleset prevents accidents and unreviewed pushes; it does not stop a deliberate owner. The GitHub audit log and the written agreement are the second layer.

Emergency fixes use the same path: a PR, CI green, review. If the process blocks a genuine emergency, change the rule deliberately, record it in `docs/handover/deploy-log.md`, and restore the rule right after.

If the host or plan cannot enforce this (for example branch protection on a private repo without a paid plan), write down which controls are missing in `docs/handover/OWNERS.md` and enforce what is possible with a server-side hook or Diskominfo Git settings.

## 13. CI pipeline

CI only calls `make`, so the same checks run on a laptop, on GitHub Actions or on a Diskominfo runner. It has **no secrets** apart from the automatic `GITHUB_TOKEN`.

| Workflow | Trigger | Does | Token permissions |
|---|---|---|---|
| `ci.yml` | pull request to `main`; push to `main` | `verify-full` (PostgreSQL 16 and 18 matrix) and `build` | `contents: read` |
| `security.yml` | weekly schedule (Monday) and manual | `govulncheck`, `npm audit`, secret scan, lockfile review (new CVEs appear without code changes) | `contents: read` |
| `release.yml` | push of a tag `v*` | re-verify, build images, SBOMs, checksums, deploy bundle, draft GitHub Release | `contents: write` only here |

**`ci.yml` in order**
1. Checkout with full history (needed for the migration check).
2. Set up Go from `api/go.mod`, Node 24, and caches for Go modules and npm.
3. Install pinned tools (goose, sqlc, tbls) with checksum verification.
4. On pull requests only: `scripts/check-migrations-immutable.sh origin/<base>` (fails if an applied migration was modified, deleted or renamed).
5. `npm ci` in `web/`.
6. `make verify-full` against a PostgreSQL service container (health-checked), matrix `16` and `18`. It includes generation check, lint, tests (including real-Postgres tests), `govulncheck`, `db-test`, `db-docs-check` and `docs-check`.
7. Separate job `build`: `make build` (Go binary and web production build). On `main` it also does a `docker build` smoke without pushing.
8. Upload test logs as artifacts when a job fails.

**Rules for the workflows themselves**
- Runner image pinned (`ubuntu-24.04`), not `latest`.
- `concurrency` group per PR with cancel-in-progress; a timeout on every job (about 20 minutes).
- Least privilege per job; no `pull_request_target`; no secrets exposed to PR code.
- Third-party actions pinned by full commit SHA; Dependabot proposes updates.
- Target total CI time under about 10 minutes. If it grows past that, split jobs before adding exceptions.
- A red `main` is the top priority. No merging while required checks are red. A flaky test is fixed or quarantined with an issue within a day, never ignored.

## 14. CD: releases and deployment

Principle: **GitHub builds and proves; it never deploys.** There are no production credentials and no SSH keys to the VPS in GitHub. Deploying is a deliberate, attributable human step on the VPS. This follows D6 ("deploy by pull or manually, no real secrets in GitHub") and D5 (Docker Compose, no Coolify or Dokploy).

Environments: local dev; **staging** (a Compose profile on the same VPS, separate ports and database, memory capped, synthetic data only); **production**.

**Release flow**
1. `main` is green; docs updated; PR titles are clear (release notes are generated from merged PR titles).
2. A maintainer creates an annotated tag `vMAJOR.MINOR.PATCH` on a commit of `main` (`v0.x` until go-live).
3. `release.yml` runs: checks the tag is on `main`; reruns `make verify-full`; runs `make release VERSION=...`, which produces:
   - API and web container images saved as a tarball;
   - `release-manifest.json`: git sha, version, image ids, tarball sha256, highest migration version, tool versions;
   - SBOMs for the images and the lockfiles;
   - `SHA256SUMS`;
   - `deploy-bundle-vX.Y.Z.tar.gz`: images, `deploy/` (compose, nginx config, scripts), migrations, manifest.
   The bundle is attached to a **draft** GitHub Release. A maintainer reviews and publishes it.
4. A maintainer downloads the bundle on their own laptop (`gh release download`, their own login) and copies it to the VPS with `scp`. **The VPS holds no GitHub credentials.** If Diskominfo later runs a registry or runner, the same bundle is produced there.
5. Deploy to **staging** with `deploy/scripts/deploy.sh vX.Y.Z --profile staging`, then `make smoke` against staging.
6. Deploy to **production** after the checklist below.

**What `deploy.sh` does on the VPS**
1. Preconditions: enough disk space; a database backup newer than 24 hours exists, or run `backup-now.sh`.
2. Verify `SHA256SUMS`; `docker load` the images; compare image ids with the manifest.
3. Run migrations (`goose up`). Because we use expand and contract, the new schema works with both the old and new application version.
4. `docker compose up -d` with the new image tags (database and nginx unchanged unless the release says so).
5. Health check and smoke script. On failure, automatically start the previous application version (the last two releases' images are kept).
6. Append an entry to `docs/handover/deploy-log.md`: who, when, version, result.

**Rollback.** Run `deploy/scripts/rollback.sh` (redeploys the previous bundle). Migrations are not rolled back automatically. A `Down` is run only after review; if a migration was not backward compatible, restore from the backup (target recovery time 4 hours, NFR-10).

**Production checklist (human, before step 6):** staging smoke passed; backup verified; release notes read for migrations and config changes; the KEK and `.env.production` are unchanged and in place; someone else knows a deploy is happening.

**Production configuration.** `.env.production` exists only on the VPS (mode 0600). The KEK is delivered as a Docker secret or systemd credential outside the repo and outside the restic backup set. Neither is ever in a bundle.

**Open points (decide after the VPS probe and the Git-host answer):** whether Diskominfo provides a registry or CI runner; whether the VPS may ever pull releases itself; the exact bundle format if Docker turns out to be unavailable (the systemd fallback must be tested before 23 Nov).

## 16. Docs rules

- Every doc under `docs/` (except `docs/schema/`) starts with `Status: canonical | generated | historical | draft` and `Last reviewed: YYYY-MM-DD`. `make docs-check` enforces this and that each doc is listed in `docs/README.md`.
- The master PRD is the Google Doc "PRD Pembangunan Ulang Situs Web Bappelitbangda Sulsel" (id `1AVENcFTXL9Oq-QnqwATAegQENVnz2FqGc2EaBnfl8UU`, v1.1 as of 2026-11-02, not yet signed). The signed original stays with the agency. The repo holds a Markdown copy at `docs/prd/PRD.md`; its header carries the version, Doc modified time, approval date and a hash. Agents never edit it; humans edit the Doc, re-export, and open a PR `docs(prd): vX.Y`. IDs (FR, NFR, OQ) are never renumbered, and `docs/prd/traceability.md` maps each id to issues and tests.
- The TDD is split: `docs/tdd/` has an overview plus one file per ADR, so two people rarely edit the same file and agents load only what they need.
- A PR that changes behaviour updates the matching TDD/ADR file in the same PR.
- Before handover, tag the TDD as the "as-built" version.
- `docs/handover/` is kept separate from working docs and stays readable without running anything.

## 17. Security lane checklist (PR template ticks these)

- Draft by agent is allowed; every line explained by the author and read by the other person.
- Design is fixed by the council/TDD: `scs` + `pgxstore` sessions, argon2id with at most 2 concurrent hashes (re-check the OWASP parameters), `Can(user, perm)` deny-by-default, lockout per account and IP, TOTP for Super Admin and Petugas PPID, KTP step-up and audit, KEK outside repo and backups, key id inside the ciphertext.
- Encryption uses a vetted AEAD (stdlib AES-GCM) with envelope encryption; no custom crypto; nonce and key storage are never left to an agent unreviewed.
- Tests exercise the real auth path plus negative authorization cases; no test-only bypass.
- Before go-live: OWASP ASVS **level 2** checklist for the admin panel, authentication and the PPID module (PRD v1.1, NFR-05, Lampiran D) and level 1 elsewhere, `govulncheck` clean, and an independent review or a network-restricted admin panel.

## 18. Rhythm

- **Daily, 10 minutes:** who owns the contract today; which tasks are open; any blocker.
- **Friday:** explain-back session (30 min); update runbook, dependency list and known-gaps list in `docs/handover/`; re-check `docs/README.md` index.
- **Weekly:** merge or close stale branches and worktrees.

## 19. Definitions of done

- **Task:** acceptance checks met; `make verify` passes (and `verify-full` if SQL or migrations changed); PR template complete; other person approved; matching docs updated; merged and branch removed.
- **Slice (vertical feature):** works end to end on the dev stack; contract, migrations, queries, handler, page and tests all merged; no open TODO that affects behaviour.
- **Release:** `verify-full` green on `main`; docs reviewed; handover items for the release updated.

## 20. Handover checklist

- One-command local run; README files accurate.
- Runbook: deploy, rollback, backup and restore, key rotation, add an admin, TOTP break-glass.
- Restore drill performed by Diskominfo staff, including decrypting a test KTP with the key.
- Dependency list with the purpose of each dependency; SBOM generated.
- `docs/handover/OWNERS.md` names the system owner and the patch owner (application and OS/VPS).
- Cold start by a Diskominfo staff member on a clean machine succeeds from the README.
- Known gaps listed honestly.

## 21. Assumptions and open items

- Two developers only; monorepo per ADR-14; hosting on one VPS.
- Open: Diskominfo Git server or private GitHub organization; whether CI can run there; whether sending code to an AI service is allowed; who owns the system after January 2027.
- This workflow rests on community and vendor evidence collected 2 Nov 2026. The evidence is thin in places: no controlled study supports spec-driven development, no government handover case study was found, and Reddit and X could not be read. The research report is in the project docs ("Team workflows with coding agents").
